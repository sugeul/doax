doax 매니페스토

Delegated Operation, Attested eXecution

위임된 작업, 증명된 실행. doax는 AI 에이전트가 사람을 대신해 쓰는 데이터·액션 리소스의 레지스트리입니다. 에이전트는 위임받은 범위 안에서만 움직이고, doax는 그 움직임을 빠짐없이 기록합니다. npm과 비슷하지만, doax가 다루는 것은 패키지가 아니라 에이전트에게 허락된 일입니다. 리소스를 찾고(resolve), 검증하고(verify), 등급을 맞춘 뒤(tier) 실행하고(invoke), 그 과정을 기록합니다(audit).

역할만으로 부족한 이유

역할기반 접근제어(RBAC)는 '누가 무엇을 할 수 있는가' 하나만을 설명합니다. doax도 이 틀을 그대로 따릅니다. 네임스페이스 소유자와 퍼블리셔가 배포할 리소스를 정하고, 토큰에는 사용자가 접근할 수 있는 네임스페이스를 담습니다. 하지만 에이전트가 사람을 대신해 일하기 시작하면 질문이 두 가지 더 생기고, RBAC는 어느 쪽에도 답하지 못합니다.

위임 (Delegation)

사람이 에이전트에게 어떤 일을, 어디까지 맡길지 정합니다. 에이전트는 맡긴 사람의 이름으로 일하지만, 리소스가 허용한 작업만 할 수 있고 리소스가 요구하는 인증 등급을 충족해야 합니다. Tier 1 리소스는 매번 사람이 직접 로그인하거나 동의해야 합니다.

증명 (Attestation)

실제로 무엇이 실행됐는지 증거를 남깁니다. 실행 전에는 패키지 다이제스트를 확인하고, 실행 후에는 누가 어떤 버전을 어떤 등급으로 실행했고 결과가 어땠는지를 지울 수 없는 기록으로 남깁니다.

원칙

  1. 위임의 범위는 에이전트가 아니라 리소스가 정한다.리소스마다 호출할 수 있는 작업이 정해져 있고, 그 밖의 작업은 호출할 수 없습니다. 내부 코드나 MCP 서버가 다른 기능을 제공하더라도 마찬가지입니다.
  2. 등급은 올릴 수만 있다.네임스페이스, 의존 리소스, 인증자는 물론 실행 중인 리소스 자신도 더 높은 등급을 요구할 수 있습니다. 반대로 등급을 낮출 수 있는 주체는 없습니다.
  3. Tier 1 동의는 사람만 할 수 있다.Tier 2~4에서는 에이전트가 스스로 다시 로그인해도 됩니다. 하지만 Tier 1 작업까지 에이전트가 승인한다면 Tier 1을 둔 의미가 없습니다.
  4. 모든 실행을 기록으로 증명한다.리졸브, 패키지 다운로드, 읽기, 드라이런, 실행, 로그인을 하나도 빠짐없이 감사 이벤트로 기록합니다. 한 번 남긴 기록은 고치거나 지울 수 없습니다. 바로잡을 때도 원래 기록은 그대로 두고, 그 기록을 가리키는 새 기록을 덧붙입니다.
  5. 실행 전에 무결성부터 확인한다.매니페스트에는 배포 시점에 계산한 패키지 다이제스트가 들어 있습니다. 내려받은 패키지의 다이제스트가 이 값과 다르면 실행하지 않습니다.
  6. 자격 증명은 실행하는 기기 밖으로 나가지 않는다.Slack, Google, ERP 같은 대상 시스템의 로그인 정보는 리소스를 실행하는 기기에만 저장합니다. 레지스트리, 코드 저장소, 인증 서버로는 보내지 않습니다.
  7. 배포한 버전은 바뀌지 않는다.한 번 배포한 버전은 고칠 수도, 지울 수도 없습니다. 그래서 감사 기록에 남은 실행을 언제든 같은 조건으로 재현할 수 있습니다.
  8. 공개 여부와 신뢰는 별개다.누가 리소스를 볼 수 있는지와 리소스가 검토를 통과했는지는 서로 다른 문제입니다. doax는 둘을 항상 따로 표시합니다.
  9. 리소스는 실패하는 방식을 미리 밝힌다.모든 매니페스트에는 예상 장애 목록이 있습니다. 실패는 괜찮지만, 목록에 없는 방식으로 실패해서는 안 됩니다.

리소스

doax가 다루는 대상은 모두 리소스입니다. 리소스의 이름은 @namespace/name@version 형식이고, 리소스마다 자신을 설명하는 JSON 매니페스트와 실제로 실행되는 코드인 패키지가 있습니다. 리소스는 네 종류이며, 종류마다 호출할 수 있는 작업이 정해져 있습니다.

종류설명작업
data-source에이전트가 읽는 레코드 컬렉션 하나describe metadata read
action외부 시스템에 변화를 일으키는 작업describe dry-run execute
authenticatorSlack, Google, Microsoft 같은 대상 시스템 하나에 로그인하는 방법describe authenticate
executor작업이 실행되는 장소 (예: 조직이 운영하는 서버)describe capabilities dispatch
  • 고정 인터페이스(Fixed Interface). doax는 종류별로 정해진 작업으로만 리소스를 호출합니다. 패키지는 직접 작성한 코드일 수도, MCP 서버일 수도 있습니다. 다만 MCP 도구는 매니페스트에서 이 작업들과 연결한 것만 호출할 수 있습니다. 실행 중에 새 도구를 찾아 리소스가 할 수 있는 일을 늘릴 수는 없습니다.
  • 매니페스트. 버전마다 하나씩 있는 JSON 문서입니다. 요약, 설명, 소유자, 요구 등급, 실행 위치, 인증자, 의존 리소스, 감사 범위, 패키지 다이제스트, 그리고 예상 장애를 포함한 서비스 수준을 담습니다.
  • 불변성. 배포한 버전은 고칠 수도, 지울 수도 없습니다. 대신 deprecated나 yanked로 표시할 수 있습니다. deprecated 버전은 경고와 함께 계속 쓸 수 있습니다. yanked 버전은 검색과 "latest" 조회에서 빠지지만, 버전을 정확히 지정하면 여전히 불러올 수 있습니다.
  • 네임스페이스. 이메일로 로그인한 뒤 원하는 이름을 직접 등록할 수 있고, 등록한 사람이 소유자로서 관리합니다. @global은 로그인한 사람이라면 누구나 쓸 수 있고, 공식 어댑터는 @doax에 있습니다.
  • 공개 범위와 검증 상태. 공개 범위(public, namespace-only, grant-list)는 누가 리소스를 볼 수 있는지를, 검증 상태(unverified, under-review, verified, rejected)는 리소스가 검토를 통과했는지를 나타냅니다. doax는 어느 한쪽을 다른 쪽의 근거로 내세우지 않습니다.

인증과 등급(Tier)

리소스는 저마다 요구하는 최소 등급을 선언합니다. Tier 1이 가장 엄격하고 Tier 4가 가장 느슨합니다.

등급이름호출 시 동작
1대화형 인증호출할 때마다 사람이 직접 로그인하거나 동의합니다.
2장기 토큰 + 호출별 권한 확인토큰으로 신원을 확인한 뒤, 이번 호출을 허용할지 한 번 더 확인합니다.
3장기 토큰만 확인토큰만 유효하면 됩니다. 감사 기록이 유일한 통제 수단입니다.
4인증 없음로그인이 필요 없습니다. 그래도 감사 기록은 익명 사용자 이름으로 남깁니다.

호출에 실제로 적용되는 등급을 실효 등급(effective tier)이라고 합니다. 실효 등급은 다음 가운데 가장 엄격한 등급으로 정해집니다.

  • 네임스페이스가 정한 하한
  • 리소스가 선언한 등급
  • 의존 리소스들의 등급
  • 인증자의 등급
  • 작업을 넘겨받은 실행 서버의 등급
  • 리소스가 실행 중에 요구하는 스텝업(step-up). 예를 들어 주문 금액이 기준을 넘을 때 요구합니다.

등급이 올라가면 그 이유도 감사 기록에 남깁니다.

로그인은 두 종류이며, 서로 섞지 않는다

  • 레지스트리 로그인(사용자 ↔ doax)을 하면 서명된 토큰을 받습니다. 이 토큰은 누구나 오프라인으로 검증할 수 있고, 사용자가 누구인지와 접근할 수 있는 네임스페이스만 담습니다. 리소스별 권한은 담지 않습니다. 현재 운영 중인 레지스트리에서는 이메일로 받은 코드로 로그인하며, doax login --web을 쓰면 브라우저에서 바로 토큰을 받아 옵니다.
  • 대상 시스템 로그인(사용자 ↔ Slack, Google, Microsoft 등)은 @doax/slack-login 같은 인증자(authenticator) 리소스가 맡습니다. 받아 온 자격 증명은 사용자와 인증자 조합별로 한 번만 저장하고, 같은 인증자를 쓰는 리소스끼리 함께 씁니다. 그래서 시스템마다 한 번만 로그인하면 됩니다.

인증자는 저마다 주체(subject)를 선언합니다. personal은 호출한 사람 본인의 자격 증명, organization은 서비스 계정, machine은 등록된 실행 서버의 자격 증명입니다. 인증자 매니페스트에는 로그인 절차 전체와 요청하는 권한, 권한을 회수하는 방법이 적혀 있어서, 검토자가 사용 전에 미리 판단할 수 있습니다.

감사와 무결성

리졸브, 패키지 다운로드, 메타데이터 조회, 데이터 읽기, 드라이런, 실행, 작업 위임, 스텝업, 로그인, 배포, 버전 상태 변경을 모두 감사 이벤트로 기록합니다. 감사 로그에는 기록을 추가할 수만 있습니다. 기록을 고치거나 지우는 기능은 아예 없으며, 바로잡을 때는 원래 기록을 가리키는 새 기록을 덧붙입니다.

각 기록에는 누가, 어떤 리소스 버전을, 어디서 실행했는지와 실효 등급 및 그 근거, 사용한 인증자, 대상 시스템, 결과를 담습니다. 액션이라면 멱등성 키를, 읽기라면 원본 데이터의 기준 시각을 함께 적습니다. 자격 증명 값은 어떤 경우에도 기록하지 않습니다.

무결성은 실행 전에 확인합니다. 패키지의 다이제스트가 매니페스트에 적힌 배포 시점의 값과 다르면 실행을 거부합니다. 감사 기록을 보낼 곳은 네임스페이스마다 정합니다. 실행 주체가 기록을 보내지 못하면 로컬에 쌓아 두고, 버리지 않습니다. 네임스페이스 소유자는 doax audit으로 기록을 조회합니다.

아키텍처

doax는 리소스를 보관하고 설명하는 서비스와, 리소스를 실제로 실행하는 실행 주체(executor)로 나뉩니다. 실행 주체는 사람을 대신해 움직이는 프로그램이라면 무엇이든 될 수 있습니다. Claude Code 같은 에이전트, 웹 앱, 배치 작업이 모두 실행 주체입니다. 실행 주체는 doax 인터페이스를 거쳐 리소스를 호출하고, 위임과 증명은 이 어댑터가 보장합니다.

서비스는 리소스를 실행하지 않으며, 대상 시스템의 자격 증명도 보지 못합니다. 실제 작업은 실행 주체 안의 doax 인터페이스가 맡습니다. 리소스를 찾아 패키지를 내려받고, 다이제스트를 확인하고, 실효 등급을 계산합니다. 이어서 인증자에게서 자격 증명을 받아 패키지를 실행하고, 감사 기록을 남깁니다.

구성 요소하는 일
실행 주체사람을 대신해 움직이는 모든 프로그램. 라이브 데모의 대시보드도 그 예로, 브라우저에서 리소스를 찾고 다이제스트를 확인한 뒤 데이터를 읽어 옵니다.
doax 인터페이스감사 기능을 갖춘 어댑터. 대상 시스템의 자격 증명을 다루는 곳은 여기뿐이며, 실행 주체는 이 확인 절차를 건너뛸 수 없습니다.
Registry Server매니페스트 보관, 검색, 리졸브, 네임스페이스 관리, 감사 기록 저장과 조회.
Code Repository불변 패키지 보관.
Auth Server로그인 처리와 토큰 발급. 토큰은 오프라인으로 검증할 수 있습니다.
Executor host회사 네트워크 안에서 실행해야 하는 trusted-executor 작업을 위해 조직이 직접 운영하는 서버. 아직 뼈대만 있습니다.

레지스트리는 npm처럼 평범한 HTTPS와 JSON으로 동작합니다. doax.io는 세 서비스를 Lambda 하나에 담아 CloudFront와 API Gateway 뒤에서 운영하며, 데이터는 Aurora PostgreSQL과 S3에 저장합니다. 온프레미스용 doax-server는 같은 세 서비스를 SQLite와 로컬 파일만으로 한 프로세스에서 실행합니다.

개발자 CLI

doax CLI는 실행 주체가 아니라 개발자 도구입니다. 같은 인터페이스를 바탕으로 리소스를 둘러보고, 시험하고, 배포하고, 감사 기록을 확인할 때 씁니다. 설치한 뒤 다음과 같이 써 보세요. 

$ doax search slack                                  # 리소스 찾기
$ doax resolve @doax/slack-post                       # 매니페스트 전체 보기
$ doax auth set @doax/slack-login                     # Slack에 한 번 로그인해 두기
$ doax read @doax/slack-channel-history --param channel=C0123456789
$ doax execute @doax/slack-post --param channel=C0123456789 \
      --param text="hello from doax" --dry-run         # 실제로 보내지 않고 미리 보기
$ doax login --email you@example.com                  # 이메일로 받은 6자리 코드로 로그인 (--web도 가능)
$ doax audit --resource @doax/slack-post              # 실행 기록 확인
명령하는 일
search, resolve리소스를 찾고 매니페스트를 보여 줍니다.
readdata-source를 읽습니다. --metadata를 붙이면 메타데이터만 읽습니다.
execute액션을 미리 보거나 실행합니다.
auth set | list | purge저장해 둔 대상 시스템 자격 증명을 인증자별로 관리합니다.
login, logout, whoami레지스트리에 로그인하거나 로그아웃하고, 내 정보를 확인합니다.
publish매니페스트와 패키지를 배포합니다.
audit내 네임스페이스의 감사 기록을 조회합니다.
registry add | list | removenpm 스코프처럼 네임스페이스별로 다른 레지스트리를 연결합니다.
app deploy정적 앱을 https://<ns>.app.doax.io에 올리고, doax 로그인으로 접근을 제한합니다.

스크립트나 CI에서도 쓸 수 있도록 모든 명령은 사용자 입력 없이 실행할 수 있습니다. --json을 붙이면 결과를 JSON 객체 하나로 출력하고, 오류가 나면 faultClass와 해결 방법도 함께 알려 줍니다. --no-input은 입력 요청을 끄고, --secret은 자격 증명을 명령에 직접 넘기며, --yes는 Tier 2 호출 확인을 미리 승인합니다.

리소스 배포

리소스는 JSON 매니페스트와 패키지, 두 파일로 이루어집니다.

$ doax login --email you@example.com
$ doax publish my-resource.manifest.json my-resource.mjs

@global에는 로그인한 사람이라면 누구나 배포할 수 있습니다. 다른 네임스페이스에 배포하려면 해당 네임스페이스의 역할이 있어야 합니다. 배포하면 레지스트리가 패키지 다이제스트를 기록하며, 이후 그 버전은 바꿀 수 없습니다.

직접 작성하는 패키지는 리소스 종류에 맞는 함수를 내보내는 ES 모듈입니다. data-source라면 describe(), metadata(), read(input)을 내보내고, read는 { data, freshness, continuation }을 반환합니다. 오류에는 매니페스트의 예상 장애 목록에 있는 faultClass 중 하나를 붙입니다.

매니페스트에는 설명뿐 아니라 서비스 수준도 밝혀야 합니다. 예상 장애마다 원인, 호출한 쪽이 받는 영향, 발생 빈도, 대응 방법을 적습니다. 성능이 떨어졌을 때의 동작과 목표 응답 시간도 함께 적습니다.

제공 방식과 진행 상황

doax는 호스팅 SaaS로 먼저 제공하고, 물리적 분리가 필요한 조직에는 온프레미스로 제공합니다. 두 방식 모두 같은 코드를 씁니다.

호스팅 (doax.io)온프레미스 (doax-server)
대상누구나. 조직마다 @org 네임스페이스를 따로 받습니다.데이터나 자격 증명이 사내망을 벗어나면 안 되는 조직
실행 환경AWS: Lambda, API Gateway, Aurora PostgreSQL, S3, CloudFront프로세스 하나. Docker 이미지나 npx doax-server로 실행하며, SQLite와 로컬 파일을 씁니다.
분리 수준접근 제어까지만. 매니페스트는 doax 인프라에 저장됩니다.물리적 분리. 상위 레지스트리 연결은 선택 사항이며, 기본으로 꺼져 있습니다.
상태운영 중빌드와 테스트는 통과했으나, 전체 흐름을 실제로 돌려 본 적은 아직 없습니다.

SaaS의 비공개 @org 리소스는 접근 제어로 보호될 뿐, 물리적으로 분리되어 있지는 않습니다. 사내망에 접근해야 하는 리소스라면 그 사내망 안에 신뢰할 수 있는 실행 서버(trusted executor)를 두어야 합니다.

아직 구현하지 않은 것

  • 호스팅 실행 서버와 trusted-executor 작업 위임. 지금은 모든 리소스를 호출한 쪽에서 실행합니다.
  • OIDC와 Google 로그인. 지금은 같은 토큰 규격을 쓰는 이메일 코드 로그인을 사용합니다.
  • 검증 심사. 검증 상태는 표시되지만, 실제로 심사하는 사람은 아직 없습니다.
  • doax-app 접근 제어. 지금은 로그인한 사람이라면 누구나 배포된 앱을 볼 수 있습니다.

기계용 매니페스토

doax 서비스가 반환하는 모든 JSON 응답에는 manifesto 필드가 있습니다. 이 필드는 doax를 소개하는 고정 문서를 가리키므로, doax를 처음 만난 에이전트도 상대가 무엇인지 알 수 있습니다. 

# 같은 내용, 기계가 읽는 형식
$ curl https://registry.doax.io/manifesto.json

이 페이지는 사람이 읽는 판이고, 기계가 읽는 판은 manifesto.json입니다.
