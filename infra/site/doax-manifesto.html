The doax manifesto

Delegated Operation, Attested eXecution

doax is a registry of the data and action resources that AI agents use on behalf of a human. An agent may act for you only as far as you delegated, and every act it takes leaves proof. It works like npm, but for what an agent is allowed to do: resolve, verify, tier, invoke, audit.

Why roles are not enough

Role-based access control answers one question: who may do what. doax keeps it: namespace owners and publishers control what gets published, and each token lists the namespaces its principal may access. But once an agent acts for a person, two more questions matter, and RBAC answers neither.

Delegation

How a person hands an operation to an agent, and within what limits. The agent acts as that person's principal. It reaches only the operations the resource exposes, and it must meet the authentication tier the resource demands. A tier-1 resource still needs the human every time.

Attestation

Proof of what actually ran. The package digest is checked before anything runs. Every operation then leaves an append-only record of who acted, which version ran, at what tier, and what happened.

Principles

  1. Delegation is bounded by the resource, not the agent.Every resource exposes a fixed, closed set of operations. Nothing outside that set is reachable, whatever the underlying code or MCP server offers.
  2. Tiers can be strengthened, never weakened.The namespace, a dependency, the authenticator, or the resource itself at runtime can demand a stronger tier. Nothing can demand a weaker one.
  3. A tier-1 consent belongs to a human.An agent may log in again by itself for tiers 2 to 4. It may never approve a tier-1 operation on its own, because then tier 1 would mean nothing.
  4. Every execution is attested.Resolves, package fetches, reads, dry-runs, executions and logins all produce audit events. Nothing can edit or delete an event; a correction is a new event that points to the old one.
  5. Integrity before execution.A manifest carries the digest of its package, taken at publish time. A package whose digest does not match is not run.
  6. Credentials stay where execution happens.Logins to target systems are cached on the machine that runs the resource. They never reach the registry, the code repository or the auth server.
  7. Published is permanent.A version never changes and is never deleted, so every audit record stays reproducible.
  8. Visibility is not trust.Who can see a resource and whether a reviewer vouched for it are separate facts, always shown separately.
  9. Resources declare how they fail.Every manifest lists its expected faults. Failing is allowed; failing in an undeclared way is not.

Resources

Everything in doax is a resource. A resource is named @namespace/name@version, described by a JSON manifest, and backed by a package: the code that runs. There are four kinds, each with its own fixed set of operations.

kindwhat it representsoperations
data-sourceOne collection of records an agent can readdescribe metadata read
actionSomething that changes the worlddescribe dry-run execute
authenticatorHow to log in to one target system, such as Slack, Google or Microsoftdescribe authenticate
executorA place where work runs, such as an org-operated machinedescribe capabilities dispatch
  • Fixed Interface. doax reaches a resource only through the operations listed for its kind. A package can be native code or an MCP server, but its MCP tools are reachable only when the manifest maps them to these operations. Dynamic tool discovery cannot widen what a resource does.
  • Manifest. One JSON document per version. It carries the summary, description, owner, required tier, execution location, authenticator, dependencies, audit scope, a digest of the package, and a service level declaration with the expected faults.
  • Immutability. A published version never changes and is never deleted. It can be marked deprecated (still resolvable, with a warning) or yanked (hidden from search and "latest", still resolvable by exact version).
  • Namespaces. Self-serve: sign in with email and claim one. The owner governs it. @global is open to anyone signed in; @doax holds the official adapters.
  • Visibility and verification. Visibility (public, namespace-only, grant-list) says who can see a resource. Verification (unverified, under-review, verified, rejected) says whether a reviewer vouched for it. One is never shown as a stand-in for the other.

Authentication and tiers

Every resource declares a minimum tier, from 1 (strongest) to 4 (weakest).

tiernamewhen the operation is invoked
1InteractiveThe person logs in or consents interactively, every time.
2Long-lived token, per-call checkA valid token proves identity; authorization is checked for this specific call.
3Long-lived token, no per-call checkA valid token is enough; the audit record is the only control.
4UnauthenticatedNo login needed; the call is still audited, with an anonymous actor.

The effective tier of a call is the strongest of: the namespace's floor, the resource's own tier, its dependencies' tiers, its authenticator's tier, the executor's tier when work is dispatched, and any step-up the resource demands at runtime (for example, an order above a threshold). The reason for any strengthening is recorded in the audit event.

Two logins, never confused

  • Registry authentication (caller to doax) yields a signed token that anyone can check offline. It carries who you are and which namespaces you may access, never per-resource permissions. The live registry signs people in with an emailed code, and doax login --web takes a token from the browser.
  • Target authentication (caller to Slack, Google, Microsoft, and so on) is done by an authenticator resource such as @doax/slack-login. The credential is cached once per caller and authenticator, and every resource that names the same authenticator reuses it, so you log in to a system once.

Each authenticator declares a subject: personal (the calling human's credentials), organization (a service account) or machine (a registered executor). Its manifest describes the whole flow, the scopes it requests and how to revoke it, so a reviewer can judge it before anyone uses it.

Audit and integrity

Every resolve, package fetch, metadata read, data read, dry-run, execute, dispatch, step-up, login, publish and lifecycle change produces an audit event. The log is append-only: no interface can edit or delete an event, and a correction is a new event that refers to the old one.

Each event records who acted, which resource version, where it ran, the effective tier and why, the authenticator used, the target system and the outcome. Actions also record their idempotency key; reads record how fresh the source data was. Credential values are never logged.

Integrity is checked before anything runs: the manifest carries a digest of the package taken at publish time, and a package whose digest does not match is refused. Each namespace chooses where its audit events go; if an executor cannot deliver them, it buffers them locally and never discards them. Namespace owners query their events with doax audit.

Architecture

doax has two sides: the services that store and describe resources, and the executors that run them. An executor is whatever program acts for the person: an agent such as Claude Code, a web app, a batch job. It calls resources through the doax interface, the adapter that adds the delegation and attestation guarantees.

The services never run a resource and never see a target credential. The doax interface inside the executor does the work: it resolves a resource, fetches its package, checks the digest, works out the effective tier, gets credentials through the authenticator, runs the package, and writes the audit event.

componentrole
ExecutorAny program acting for a person. The live demo dashboard is one: a web page that resolves, checks digests and reads resources in the browser.
doax interfaceThe adapter with auditing. The only part that touches target credentials; an executor cannot skip its checks.
Registry ServerManifests, search, resolution, namespaces, audit storage and query.
Code RepositoryImmutable package storage.
Auth ServerSign-in and offline-verifiable tokens.
Executor hostAn org-operated machine for trusted-executor work that must run inside a company's network. Scaffold only.

The registry is plain HTTPS and JSON, like npm. On doax.io the three services run as one Lambda behind CloudFront and API Gateway, with Aurora PostgreSQL and S3. The on-premise build, doax-server, runs the same three in one process with SQLite and local files.

The developer CLI

The doax CLI is not an executor. It is the developer's tool for exploring, testing, publishing and auditing resources, built on the same interface. Install it, then: 

$ doax search slack                                  # find resources
$ doax resolve @doax/slack-post                       # print the full manifest
$ doax auth set @doax/slack-login                     # log in to Slack once, cached locally
$ doax read @doax/slack-channel-history --param channel=C0123456789
$ doax execute @doax/slack-post --param channel=C0123456789 \
      --param text="hello from doax" --dry-run         # preview, no side effects
$ doax login --email you@example.com                  # 6-digit code by email (or --web)
$ doax audit --resource @doax/slack-post              # see what was done
commandwhat it does
search, resolveFind resources; print a manifest
readRead a data-source, or its metadata with --metadata
executeDry-run or execute an action
auth set | list | purgeManage cached target credentials, grouped by authenticator
login, logout, whoamiRegistry sign-in and identity
publishPublish a manifest and its package
auditQuery the audit log for your namespaces
registry add | list | removeRoute a namespace to a different registry, like npm scopes
app deployHost a static app at https://<ns>.app.doax.io behind doax sign-in

For scripts and CI, every command runs without prompts: --json gives one JSON object with a faultClass and a fix on errors, --no-input disables prompts, --secret supplies a credential inline, and --yes grants a tier-2 per-call check.

Publishing a resource

A resource is two files: a JSON manifest and a package.

$ doax login --email you@example.com
$ doax publish my-resource.manifest.json my-resource.mjs

Anyone signed in can publish to @global; other namespaces need a role in that namespace. The registry records a digest of the package, and the version can never change after that.

A native package is an ES module that exports the operations for its kind. For a data-source those are describe(), metadata() and read(input); read returns { data, freshness, continuation }. Errors carry a faultClass that matches the manifest's list of expected faults.

The manifest has to declare its service level, not only describe itself: each expected fault with its trigger, its effect on the caller, how often to expect it and what to do, plus the behaviour under degradation and the latency target.

Deployment and status

doax runs as hosted SaaS first, with on-premise for organizations that need physical isolation. Both use the same code.

hosted (doax.io)on-premise (doax-server)
ForAnyone; each org gets its own @org namespaceOrgs whose data or credentials must never leave their network
Runs onAWS: Lambda, API Gateway, Aurora PostgreSQL, S3, CloudFrontOne process: Docker image or npx doax-server, SQLite and local files
IsolationAccess control only; manifests live on doax infrastructurePhysical; optional link to an upstream registry, off by default
StatusLiveBuilds and passes tests; not yet run end to end

Private @org resources on SaaS are access-controlled, not isolated. A resource that has to reach a company's internal network needs a trusted executor inside that network.

Not built yet

  • Hosted executors and trusted-executor dispatch. Today every resource runs where its caller runs.
  • OIDC and Google sign-in. Email-code login is used instead, with the same token contract.
  • Verification review. Resources show a verification status, but nobody reviews them yet.
  • Access control for doax-app. Any signed-in user can view any deployed app.
